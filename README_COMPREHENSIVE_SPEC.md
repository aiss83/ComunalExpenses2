# ТЕХНИЧЕСКАЯ СПЕЦИФИКАЦИЯ (ТЗ)
## Проект: Система учета общих расходов ресурсов (СУОР)

**Дата создания:** 18.06.2026
**Версия:** Initial Draft / Baseline v1.0
**Цель документа:** Детально описать техническую архитектуру, бизнес-логику и физическое устройство приложения.

---
### 1. Общие положения и Цель Проекта

**Назначение:** Мобильное приложение на основе KMP для учета и мониторинга потребления общих ресурсов (вода, электричество) в замкнутом сообществе.
**Архитектура:** Реализовано по принципу **Чистой Архитектуры (Clean Architecture)**, что обеспечивает изоляцию бизнес-правил от деталей реализации UI или СУБД.

### 2. Архитектура Программного Обеспечения (High-Level View)

Приложение разделено на три логических слоя, каждый из которых выполняет строго оговоренную функцию.

#### 2.1. Презентационный Слой (UI / Presentation Layer)
*   **Назначение:** Визуальное представление данных и сбор пользовательского ввода.
*   **Реализация:** Compose UI (`commonMain`). Соответствует текущим экранам: `HomeScreen`, `SettingsScreen`, `AddResourcesDataScreen`.
*   **Роль:** Обмен данными с Domain Layer через специализированные компоненты.

#### 2.2. Доменный Слой (Domain Layer)
*   **Назначение:** Сердце приложения. Содержит все бизнес-правила, которые являются неотъемлемой частью учета расходов.
*   **Реализация:** ViewModels (`ResourcesDataViewModel`, `SettingsViewModel`).
*   **Взаимодействие:** Он не знает, как данные хранятся. Он только знает *контракт* о том, что он должен запросить у Репозитория.

#### 2.3. Слой Данных (Data Layer)
*   **Назначение:** Абстракция всех операций ввода-вывода. Он изолирует Доменный слой от специфики СУБД.
*   **Структура:** Многоуровневая модель:
    *   **`ResourceDataRepository.kt` (Интерфейс):** Главный контракт для Доменного слоя. Реализует высокоуровневые операции: `getAllResourceData()`, `insertResourceData(data)`.
    *   **`ResourceDataDao.kt` (Исполнитель):** Низкоуровневое взаимодействие с базой данных. Выполняет команды SQLDelight (`INSERT`, `SELECT`, `UPDATE`).
    *   **`DatabaseFactory.kt`:** Управляет жизненным циклом подключения к базе данных.

---
### 3. Схема Базы Данных (Persistence Layer)

База данных реализуется на основе `SQLDelight` и является источником истины для всех измерений.

#### 3.1. Физическая Сущность: `resources_records`
*   **Таблица:** `resources_records`
*   **Назначение:** Хранение атомарных измерений потребленных ресурсов.

| Атрибут (Поле) | Тип данных | Назначение | Ограничения |
| :--- | :--- | :--- | :--- |
| `recordId` | TEXT | Уникальный идентификатор записи. | PRIMARY KEY (PK). |
| `date` | INTEGER | Дата измерения. | NOT NULL. Хранится в числовом формате (предполагаемый Timestamp).|
| `waterHot` | INTEGER | Потребление горячей воды. | NOT NULL (Default 0). Единицы измерений должны быть согласованы на уровне приложения. |
| `waterCold` | INTEGER | Потребление холодной воды. | NOT NULL (Default 0). |
| `electricityDay` | INTEGER | Электричество (день). | NOT NULL (Default 0). |
| `electricityNight` | INTEGER | Электричество (ночь). | NOT NULL (Default 0). |

#### 3.2. Доступ к данным (DAO Operations)
Операции выполняются посредством методов `ResourcesRecords.sq`: выборки (`SELECT`) и транзакции (`INSERT`/`UPDATE`/`DELETE`).
